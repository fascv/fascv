PROJECT START FILE
As of: 2026-03-16

What this project is
- This repo runs a Binance USDC rotation trader.
- It scans a broad Binance `USDC` universe of roughly `135` symbols, builds an inner watch/live pool of up to `28` names, selects up to `4` true active slots, and trades those coins with per-lane runtimes.
- The system has a local learning layer plus an OpenAI-based meta layer.
- The OpenAI layer is overgeordnet only. It does not place orders directly.

Main architecture
- Full USDC universe / shadow scan:
  - Broad scan and candidate generation over many Binance USDC symbols.
  - Important scripts:
    - `scripts/select_rotation_watchlist.py`
    - `scripts/scan_shadow_usdc_scalp_universe.py`
- Watch pool:
  - Up to `28` symbols are kept as the current live watch/watchable pool.
  - Runtime env file:
    - `configs/rotation_watch_pool_runtime.env`
  - Refresh script:
    - `scripts/rotation_refresh_watch_pool.py`
- Active slots:
  - Current architecture is effectively "capital slots", not rigid strategy silos.
  - Usually 4 slots maximum, capital split across active selections.
  - Current state file:
    - `configs/rotation_active_lanes.json`
- Lane runtimes:
  - Each selected symbol gets its own generated runtime config under:
    - `logs/rotation_runtime_configs/`
  - Apply / reload path:
    - `scripts/rotation_apply_active_lanes.py`
  - Core launch / reload path:
    - `trading/launch.py`
    - `trading/processes/core.py`

Capital / slot model
- The broad USDC pool, the watch/live pool, and the 4 active slots are different layers.
- The practical model is:
  - about `135` names in the broad USDC universe
  - up to `28` names in the current watch/live pool
  - up to `4` names as the true active capital slots
- The 4 slots exist mainly to split available capital across up to 4 active opportunities.
- It is valid for fewer than 4 to be active when gates do not allow more.
- Never treat the symbol snapshot inside this file as current truth.
- Always read the live state fresh from:
  - `configs/rotation_active_lanes.json`
- Important dashboard interpretation:
  - `selected = true` means one of the active `4`
  - `running = true` can also include extra watch-pool lanes
  - seeing more than `4` live rows is not automatically wrong

Strategy layers
- Meta / selector strategy names are newer and descriptive:
  - `staircase`
  - `pullback_continuation`
  - `breakout_retest`
  - `relative_strength`
  - `rebound`

- Live core alpha families are fewer and simpler:
  - `trend`
  - `mean_reversion`

  - `auto`
- Current mapping that was intentionally implemented:
  - `staircase -> continuation`
  - `pullback_continuation -> continuation`
  - `breakout_retest -> breakout`
  - `relative_strength -> trend`
  - `rebound -> swing`
  - `continuation -> continuation`
  - `breakout -> breakout`

What the OpenAI layer does
- OpenAI is used only for the meta-controller layer.
- It recommends things like:
  - profile
  - risk mode
  - strategy weights
  - strategy actions / slot preference
  - candidate overrides
  - avoid symbols
- The OpenAI path does not directly trade and should stay overgeordnet.
- Main files:
  - `trading/meta/openai_meta.py`
  - `scripts/rotation_meta_shadow.py`
- Current OpenAI settings:
  - model: `gpt-5.1`
  - minimum OpenAI interval: `15` minutes
  - timeout: `40` seconds
- Important:
  - Local meta / shadow logic still runs every `5` minutes.
  - OpenAI output is reused between calls.

Learning chain
- The system learns mainly through the shadow/meta path.
- Main file:
  - `trading/meta/rotation_shadow.py`
- It does not learn from the UI directly.
- It builds trade samples from real fill events in the lane journals.
- It also builds no-trade / counterfactual samples for blocked opportunities.

What the learning currently analyzes
- Realized trade outcomes:
  - PnL
  - win rate
  - hold duration
  - exit reason
  - strategy at entry
- Post-exit path:
  - `5/15/30/60/120` minute follow-through
  - missed run after exit
  - early exit patterns
  - shakeout-then-run patterns
  - micro-pop-loss-run patterns
- Counterfactual no-trades:
  - blocked setups are followed afterwards to judge whether the block was likely right or too strict
- Regime / session breakdown:
  - learning is no longer purely global

Very important learning truth
- The learning basis is the shadow trade reconstruction, not the dashboard "Live Coins" number.
- The dashboard can still be wrong or misleading if it shows a current lane-level live value.
- The learning path should use:
  - fill-based trade samples from journals
  - reconstructed trade PnL
  - post-exit follow-through
- The learning path should not use:
  - dashboard live coin PnL
  - ad-hoc UI totals
  - manually interpreted open-position values

PnL truth and pitfalls
- Binance trade history is the closest ground truth.
- The bot reconstructs PnL locally from Binance-derived fills.
- Important files:
  - `trading/binance/rest.py`
  - `trading/processes/exec.py`
  - `trading/meta/rotation_shadow.py`
- Major past bug:
  - old residual position / sync state could leak into new trade reconstruction
  - this created false positive strategy PnL in the dashboard and in learning
- This was already fixed by tightening trade sample extraction and position sync handling.
- Important consequence:
  - if a new chat sees strategy PnL on the dashboard, it should not trust it blindly without checking journals / Binance.

Main root cause of losses found so far
- The biggest recurring problem has not been missing entries.
- The biggest recurring problem has been too-early exits and repeated re-entry whipsaws.
- Typical bad pattern:
  - buy
  - tiny move
  - early exit or hard stop
  - re-buy too soon
  - another quick loss
- This pattern appeared on symbols like:
  - `BANANAS31`
  - `ALGO`
  - `ZAMA`
  - earlier also similar on others

Important fixes already implemented

- Runtime config reloads can switch strategy/alpha state without a full core restart.
- Selector strategy choices are bridged into executable runtime alpha families.
- The OpenAI prompt and the learning path now care about too-early exits and blocked no-trades, not only realized PnL.
- Contaminated trade samples from sync-expanded / mixed campaigns are dropped instead of learned.
- Restart / sync handling restores the right entry state more reliably after reloads.
- Small-position / min-notional handling was tightened so the bot does not create unsellable dust trades.
- Same-symbol re-entry protection exists now as:
  - weak-exit cooldown
  - whipsaw hard-stop cooldown
  - repeated short-loss cluster cooldown
- The generic lesson from the older BANANAS31-style failures is:
  - the real issue was not just "cooldown too short"
  - the real issue was losing flat reentry state across restarts and then re-buying too soon

Selector / market reality
- Low trade count is often not a broken buy path.
- It is often:
  - poor market structure
  - `edge_below_costs`
  - bottom / lift-off / post-dump candidates with no clean setup yet
  - guarded profile being selective
- Old universe names like `OP`, `HBAR`, `DOT`, `ESP` are not generally "banned".
- Often they simply fall out of the current top watch ranking because their live structure is weak.
- The system can run with fewer than 4 active names if gates do not justify more.
- This is not automatically a bug.
- Raw selector snapshots may still occasionally contain older meta labels.
- For live tuning, catalog work, and lab revisions, only treat these as the core strategy targets:
  - `staircase`
  - `continuation`
  - `breakout`
  - `rebound`

How to debug a suspicious trade
1. Check the symbol journal first.
2. Look for:
   - `fill` events
   - `core_decision`
   - `core_signal`
   - `core_account_synced`
   - `exec_core_account_sync`
3. Confirm:
   - actual buy / sell times
   - exit reason
   - whether state was recovered or restarted in the middle
4. Check the active runtime config for that symbol.
5. Only after that compare with Binance trade history.

Known truths for future chats
- The user cares most about net profit, not abstract elegance.
- The user does not want the OpenAI layer to trade directly.
- The biggest historical loss source has been bad exits, not missing entries.
- "Learning" should not simply make the bot trade less and less.
- If the bot exits too early, the answer is to improve exit handling, not just ban the entry.
- Manual interventions should be avoided because they make diagnosis and learning dirtier.
- If a dashboard number looks wrong, assume it may be a UI/status artifact until proven against journals / Binance.

1. Current carry-forward truths
- The rotation system is running in the current `135 -> up to 28 -> up to 4` model.

2. Trader-side truths
- The sell/reconcile path is materially cleaner than before:
  - duplicate flatten / emergency exits are suppressed while an older exit is inflight
  - synthetic `account_sync_delta` sell artifacts are suppressed while open orders still exist
  - dust-only sync deltas below min-notional are ignored
  - relay local trade reports now ignore `account_sync_delta` pseudo-fills
- `time_break_even_floor` no longer acts as a deep-loss time stop before any near-break-even excursion.
- `time_break_even_floor` also no longer cuts a fresh continuation bottom-reclaim like the `RENDER` sell from `2026-03-16`.
- Flat reentry state is restored from journals after restart, so same-symbol loss-cluster / cooldown state should survive lane restarts.
- Dashboard trade reports now default to `auto`, which prefers the local Binance trade mirror and falls back to journals only if no mirror data exists.
- The first real `24h` audit showed that the problem is not just UI:
  - journal-vs-Binance mismatches are real on several symbols
  - examples included `SHIB`, `CFX`, `RENDER`, `FET`, `VIRTUAL`
  - some symbols existed only on the journal side, others only on the Binance side
- Important consequence:
  - dashboard PnL should prefer the Binance mirror
  - learning / labs still need journal decision context, but trade samples are now mirror-annotated before lab use
  - `rotation_strategy_lab` and `rotation_replay_lab` now keep only `mirror_verified` trade samples for scoring
  - partial mirror matches (`time_qty_only`) stay visible in the reports, but they are not used as learning evidence
  - before a new lab rerun, run `audit_trade_mirror_coverage.py`; if mismatch count is high, treat the sample as contaminated
- Plain-language rule for future chats:
  - Binance is the source of truth for what really bought and sold.
  - Local journals are the source of truth for why the bot decided to act.
  - The dashboard should therefore trust the Binance mirror first for realized trade results.
  - The labs should not learn from journal-only trades anymore.
  - The practical learning source is now: local bot decisions plus Binance-confirmed fills.
  - If many recent trades cannot be confirmed against Binance, treat the sample as dirty and do not trust a fresh lab rerun.
